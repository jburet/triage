# 0019 — A service is mapped to its repository by the image it is running

Status: Proposed. Demotes M3's `serves` patterns from the rule to the fallback.

## Decision

Which repository a running service is, is derived from **the image name in that
service's own change events**, and from nothing else. The ladder, in order, and each
rung is recorded on the answer:

1. **The derived workload** (`workloads`, keyed on the service name Datadog uses).
   Its `source` says how it was derived: `image` when a container-start or
   StatefulSet change event named the image, `pattern` when none did.
2. **F0's system map**, which is keyed on the name a repository *says* it deploys as.
3. **`config.yaml`'s `serves` patterns**, the M3 stopgap.

Three rules make the derivation refuse rather than guess:

- **An image no repository in the seed is named after is a stated failure carrying
  the image**, never the nearest repository name. A mapping that is wrong sends every
  later analysis into a tree this service does not run, and says nothing about having
  done so.
- **Only a mono-tenant repository may run under a name that is not its own.** The seed
  says which repositories those are; a multi-tenant repository seen under a second name
  is reported as a conflict and no row is written.
- **The rung is carried to the diagnosis.** A repository a `serves` glob picked out
  caps confidence at `medium` and appends a sentence saying the commit is the
  repository's last summarised one rather than this service's build.

The seed — tenancy and deploying IaC repository per repository — is not discoverable
from any cluster. It is parsed from the architecture document into
`config/repository-map.yaml`, generated by a script and reviewed as a diff, because the
document is someone's Markdown and will be edited without telling us.

## Why

F0 keys the system map on the name a repository says it deploys as. That is right for
the thirteen multi-tenant applications and wrong for the one that matters most:
`platform` is mono-tenant, one StatefulSet per customer, so what alerts and what
Datadog tags is `plt-merck-qa`, `plt-hcl-software-uat` — one name per tenant, none of
which any repository claims. Every alert from the pod-down monitor resolved to *"service
is not in the system map"*, and the analyses that give Triage its reason to exist never
ran.

`serves: ["plt-*"]` fixed that and is a hand-maintained list of guesses about naming. It
is right until a customer is provisioned under a name nobody anticipated, and it is
silently wrong rather than loudly wrong: a glob that matches the wrong repository
produces a confident analysis of the wrong tree.

The running workload already names its own repository, and Triage already collects it.
Every container start event in an incident collection carries `short_image:platform`,
`platform@sha256:2e15f697…`, and every application image is built into the infra
account's ECR under the repository's own name. So the fact is *observed* rather than
declared, it covers a customer provisioned five minutes ago, and it is free — the events
are already in the collection.

Patterns stay as the fallback because Datadog retains events for a bounded window: a
service that has not restarted inside it emitted no image, and a mapping from a person's
statement beats no mapping at all — provided the diagnosis says which it had.

## Consequences

- A `workloads` table, one row per running service, upserted by a `service_mapping`
  graph with no model call anywhere on its path: everything it joins is already
  structured.
- A mapping pass reports itself to the platform channel — mapped by image, mapped by
  pattern, unmapped, conflicting, and mapped-but-chart-not-found. An unmapped production
  workload is Triage's own gap, not the owning team's.
- Re-deriving a service whose image digest is unchanged rewrites nothing and asks GitHub
  nothing, on [ADR-0015](0015-incremental-refresh-unit.md)'s reasoning one level down.
- **Nothing maps until the real repositories are declared in `config.yaml`.** Against
  the shipped example all twenty seed repositories come back unclaimed. That is correct
  and it is also the whole report.

## What this does not see

- A service that never alerts and is not in the document. Enumerating an AWS account is
  a different feature with different credentials.
- A repository added, or a tenancy model changed, since the document was written
  (2026-04-20). The generated file makes the drift visible as a diff, which is the most
  that can be done from here.

## Revisit when

An image is renamed away from its repository — `platform` published as
`zeenea-platform`, a monorepo publishing three images. The mapping then fails loudly,
as a line in the report, which is the point; the fix is a declared image-to-repository
alias in `config.yaml`, not a fuzzy match. If instead the *events* stop carrying images
— a change in the Datadog agent, a collection window narrowed past the last restart —
the derivation quietly degrades to the patterns for everything, and the report's
"mapped by pattern" count is where that shows up.
